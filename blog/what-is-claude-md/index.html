What is CLAUDE.md and how to use it

2026-08-06 · echov4ult

CLAUDE.md is a simple text file that tells Claude Code how to work in your project. You write your rules and preferences in it once, and Claude reads them at the start of every conversation. No more repeating yourself.

The problem it solves

Every time you start a new conversation with Claude Code, it starts fresh. It doesn't remember what you told it yesterday. If you spent ten minutes explaining "we use this testing setup" and "never change that config file," that's gone next session. You're explaining it again.

CLAUDE.md fixes that. It's a file you create in your project folder, and Claude reads it automatically before doing anything else. Think of it as a sticky note on the fridge, except the fridge actually reads it.

I run a multi-agent Claude Code setup for my own products, and my CLAUDE.md files are the single most valuable piece of infrastructure I have. Not because they're clever. Because they stop me from explaining the same thing twice a day.

What goes in it

Plain English. Seriously, that's it. You're writing a note to a very capable assistant who forgets everything between conversations. Tell it:

  • What commands to use (and which ones to avoid)
  • How your project is organized
  • Rules that matter: "always run tests before saving," "never touch the database directly"
  • Style preferences: "use tabs, not spaces" or "keep function names descriptive"

You don't need special formatting or programming knowledge. A simple list of rules works fine. Here's what a basic one looks like:

# Project rules

- This is a React app using TypeScript
- Run `npm test` before committing any changes
- Never install new packages without asking first
- Components go in src/components/
- We use 2-space indentation

That's a real, working CLAUDE.md. Nothing fancy. Five lines, and Claude will follow every one of them in every conversation you have in that project.

Where to put it

Create a file called CLAUDE.md (all caps, with the .md extension) and drop it in your project's main folder. Claude Code finds it automatically.

There's a shortcut if you don't want to start from scratch: type /init inside a Claude Code session and it will scan your project and write a starter file for you. You can tweak it afterward. Takes about thirty seconds.

The three levels (if you want to get organized)

You can actually have CLAUDE.md files in different places, and they stack like layers. Most people only need the first one, but here's the full picture:

Project rules (CLAUDE.md in your project folder). This is the main one. It applies to everyone working on the project. Think of it as the rules posted in the office kitchen. "Clean up after yourself. Label your food. Don't microwave fish."

Personal preferences (~/.claude/CLAUDE.md, which means a file in your home directory). Rules that follow you across every project on your computer. Like "I prefer short explanations" or "always show me what changed." These are your house rules.

Private notes (CLAUDE.local.md in your project folder). Just for you, not shared with teammates. A sticky note on your own monitor. "I'm currently refactoring the login page" or "my test server runs on port 5433."

When rules from different levels disagree, the more specific one wins. Project rules override personal preferences. Private notes override project rules. Claude reads them all, but it treats the closest-to-the-work instructions as the final word.

What to leave out

This is where most people go wrong, and I learned it the hard way. My first CLAUDE.md was close to 300 lines. Claude followed maybe half the rules in it.

The reason: Claude has a limited attention budget each session. Everything in your CLAUDE.md takes up space in that budget. When you fill the file with obvious stuff, the important rules get diluted. Anthropic recommends keeping the file under 200 lines. From experience, 50 to 80 lines works even better.

Skip these:

  • Things Claude can figure out by looking. It can read your project files. You don't need to describe your folder structure in CLAUDE.md.
  • Long step-by-step procedures. If a process takes more than five steps to explain, it belongs in a separate file called a "skill" (that's a different Claude Code feature for reusable workflows; there's a full breakdown of skills vs. subagents vs. commands if you're curious).
  • Rules nobody actually follows. If your CLAUDE.md says "100% test coverage" but your project has 40%, Claude gets mixed signals, not motivation.

Every line should earn its keep. If a rule isn't saving you from explaining something every session, it's just noise.

One feature most people miss

Your CLAUDE.md can pull in other files. Write @docs/api-notes.md on a line by itself, and Claude loads that file's contents automatically. This keeps your main file short and focused while giving Claude access to detailed reference material when it needs it.

There's also a feature called "path-scoped rules" where you can create separate rule files in a .claude/rules/ folder that only apply when Claude is working on certain types of files. Your React rules load when Claude edits React files; your database rules load when Claude touches migration scripts. It keeps things tidy, and Claude doesn't waste attention on rules that don't apply to the current task.

FAQ

Does Claude remember my CLAUDE.md between conversations?
Claude re-reads the file from scratch at the start of every conversation. It doesn't "remember" the file so much as re-read it, like checking the employee handbook every morning. That's actually the advantage: you can update the file anytime and Claude picks up the changes immediately.

What's the difference between CLAUDE.md and "auto memory"?
You write CLAUDE.md. Claude writes auto memory. Auto memory is Claude's own notebook, filled with things it noticed during your sessions: "this person prefers short variable names," or "the build command is npm run build, not yarn build." Both load every session, but CLAUDE.md holds your rules, and auto memory holds Claude's observations.

I set up a CLAUDE.md but Claude isn't following the rules. What's wrong?
First, type /context in Claude Code to check that the file actually loaded. If it loaded and Claude still ignores a rule, the issue is usually vague wording. "Format code nicely" doesn't give Claude much to work with. "Use 2-space indentation and always add semicolons" does. Be specific. Think instructions, not wishes.

Can I use CLAUDE.md on a team?
Yes, and it's one of the best uses. Put CLAUDE.md in version control (like Git) so everyone shares the same rules. Each person can add their own personal preferences in a CLAUDE.local.md file that stays off the shared repo.

How is this different from a regular README?
A README is for humans. CLAUDE.md is for Claude. There's nothing stopping you from having both, but don't copy-paste between them. Claude can already read your README if it needs to. CLAUDE.md is for directives: "do this, never do that." Short, direct, no explanations needed.

Open Claude Code in any project and type /init. Thirty seconds, and you have a starter CLAUDE.md based on your actual codebase. Then add one rule. Just one. Something you've corrected Claude on before. That single line will save you from ever explaining it again.
