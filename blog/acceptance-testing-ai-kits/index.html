Acceptance-testing an AI kit: 22 scenarios before we'd sell it

2026-07-26 · echov4ult

If your product installs files into someone's project, 'it worked on my machine' is not a QA strategy.

Full Party is mostly markdown — agents, workflows, templates. The one piece of real software in the box is the installer, and that's exactly where a digital product earns refunds or trust. Before listing it, we wrote an acceptance suite: 22 scenarios that must pass on a fresh build, every time anything changes.

What the 22 scenarios cover

  • Clean installs — into an empty project, a populated project, and a project that already uses Claude Code.
  • Hostile paths — directories with spaces and unusual names, because customer machines are not demo machines.
  • Collisions — a same-named agent file already exists. Required behavior: list the conflict and stop, changing nothing. An installer that overwrites customer files is a lawsuit with a progress bar.
  • Lifecycle — upgrade with backup, uninstall, reinstall. If you sell v1.x updates, the upgrade path is a feature and gets tested like one.
  • Verification — a verify script the customer can run to confirm their install matches the manifest.

The part most people skip: sabotage the checks

A test suite that has never failed is unproven — maybe the checks work, maybe they're checking nothing. So we break things on purpose: delete a file the verifier should catch, corrupt a path, plant a collision. If the check still passes, the check was theater. Every gate in the suite has been made to fail at least once on purpose. That's what makes its passes meaningful.

Why this matters for AI-built products specifically

AI assistants write installers quickly and confidently — and confidently is the problem. Generated code fails in the gap between what you asked for and what you'd have asked for if you'd thought of it: the space in the path, the pre-existing file, the second run. Acceptance scenarios are how you think of it before a customer does. The suite runs on every build; the count in our listing — 22/22 — is re-generated, not remembered. (See also: the recheck rule, which is how a stale version of that very claim got caught.)

Steal this

Whatever you're shipping — a prompt pack with an install script, a plugin, a template repo — write the scenario list first: every way installation can start, collide, upgrade, and end. Automate what you can, script the rest, sabotage each check once. It's a day of work that upgrades "I think it works" to a number you can print on the listing.
