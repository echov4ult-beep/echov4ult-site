Why is my multi-agent setup so slow? Because it's a queue, not a graph

2026-07-27 · echov4ult

Quick answer: your setup is slow because it runs as a queue. Each agent waits for the one before it, even when it doesn't use anything that agent produced. Draw the work as a graph instead: keep an arrow between two steps only when real data flows across it, run everything without an arrow at the same time, and merge the results with plain code. Claude Code's dynamic workflows exist for exactly this.

I run a real multi-agent setup: an eight-agent business crew plus a game-studio roster. Here's the uncomfortable thing about most "multi-agent pipelines," mine included, most days: only one agent is actually working at any moment. The rest are waiting in line.

That's not a bug in Claude Code. It's the default. Unless you ask for something else, the main session decides what to spawn next, waits for the result, reads it, and spawns the next thing. Turn by turn. A queue with good manners.

A queue is fine for small jobs, and it's the cheapest shape there is. It becomes a problem when your steps don't actually depend on each other. Most of the time, they don't.

(Credit where due: the queue-vs-graph framing clicked for me reading a long X piece on graph engineering by @0xCodez. This post is that idea run through my own setup, with my own receipts.)

In simple terms

Picture one clerk with five errands: bank, post office, pharmacy, hardware store, groceries. He does them in the order you wrote them down, and the trip eats the whole afternoon. Nothing about the pharmacy depends on the post office. Send five people out with one errand each and have them meet back at the kitchen table, and the afternoon collapses into twenty minutes plus one conversation to put it all together.

That's the entire idea. "Multi-agent" should mean the team that splits up. Most setups are the one clerk holding a longer list.

The edge test: "and then" is not a dependency

Write your pipeline as a list of steps. At every "and then," ask one question: does the next step read the previous step's output?

If yes, that's a real dependency. Keep the arrow. If no, the second step was only waiting out of habit. Delete the arrow, and the two steps can run at the same time.

Take "research competitor A, then competitor B, then competitor C, then compare them." The compare step reads all three write-ups, so its arrows are real. But B never reads A's notes, and C never reads B's. Run the edge test and a four-step line collapses into three agents working at once plus one that waits for all of them.

The word "then" in your prompts is the culprit. It smuggles in dependencies that don't exist.

The diamond: fan out, merge with code, judge once

Once you start deleting fake arrows, most big jobs settle into one shape: wide in the middle, narrow at both ends. Fan independent workers out. Collect what they return. Merge, dedupe, and filter the pile with plain code. Hand one clean list to a single agent for the final judgment call. A diamond.

Claude Code has a native mechanism for this: dynamic workflows. You describe the job and ask for a workflow (or type the keyword ultracode), and Claude writes a short JavaScript script that spawns the subagents and runs in the background. Intermediate results live in script variables instead of the context window, so your session only ever sees the final answer.

A stripped-down diamond, in the flavor I care about (game dev):

// fileList = a tiny JSON Schema: an object with a files array
const scenes  = await agent('List every scene file under game/scenes/.', { schema: fileList })
const checks  = await pipeline(scenes.files, s =>
  agent(`Check ${s} for placeholder art. Return null if clean.`, { label: s }))
const flagged = checks.filter(Boolean)  // the merge: plain JS, no model call, zero tokens
const report  = await agent(`Rank these flagged scenes by player impact: ${JSON.stringify(flagged)}`)

Two details carry the weight. First, give each worker a schema so it must return structured data instead of prose; the middle of the diamond should be a list your code can filter, not paragraphs your next agent has to interpret. Second, look at the merge line. It costs nothing, because no model runs. If you ever catch an agent whose whole job is summarizing what other agents said so it can pass the summary along, stop: you're paying tokens for work a for-loop does free.

Put a skeptic on the edge

My house has one law older than any of this: nothing ships checked once. Every artifact gets a second pass that tries to prove it wrong, not confirm it right. In one launch week that rule caught a stale test log, a phantom feature in my own marketing copy, and a discount nobody had approved.

A graph turns that law from a habit into a structure. Between "an agent found something" and "the report says something," insert a verifier: an agent that reads the finding cold and tries to kill it. Only survivors count. Claude Code's bundled /deep-research workflow already works this way: it cross-checks sources against each other and filters out claims that don't survive.

It's the same reason I ran 22 acceptance scenarios against my own kit before I'd sell it. One pass produces plausible. An adversarial pass produces true.

Loops have to converge

Some jobs are loops: hunt for problems, verify them, hunt again, repeat until the codebase runs dry. Two rules keep a loop from becoming a token furnace.

Stop on dry rounds, not on a hunch. Give the loop a hard exit: two rounds in a row with nothing new means done. That's the shape the official docs suggest for jobs like flaky-test hunts, and it's the difference between a loop and a subscription.

Dedupe against everything you've seen, not just what you've confirmed. This one bites people. If round three only checks new findings against the confirmed list, every dead end your verifier already rejected comes back next round, and you pay to refute the same ghost forever. The seen list includes the rejects.

Cheap models on boring nodes

Every agent in a workflow inherits your session's model unless the script routes a stage elsewhere. That's a bill waiting to happen. Listing files does not need your biggest model. Neither does checking one scene for placeholder art. The final synthesis — the ranking, the judging, the report — does.

So check /model before you launch a big run, and when you describe the task, say which stages can use a smaller model. Judgment gets the expensive brain. Clerical work gets the cheap one.

What this costs, honestly

Fan-outs are opt-in, and they should be. A workflow run can use meaningfully more tokens than working the same task in conversation. Claude Code itself warns you when a run schedules more than 25 agents or projects past 1.5 million tokens. Those numbers should tell you something.

My rule: the graph is for jobs one context window genuinely can't hold. Repo-wide audits. Big migrations. Research that needs sources cross-checked. For everything else the queue is fine, and cheaper, and I still use it daily.

And notice what the graph is not: an excuse for a bigger roster. I run ten agents, and most days six do the work. Topology beats headcount. I'd bet on a well-shaped diamond of five agents over an unshaped swarm of forty, and the diamond is the cheaper bet. That thinking is baked into Full Party too: a small roster with real verdict roles, including a critic whose only job is to fail work that isn't ready.

Try it yourself

Take the biggest multi-step job you gave Claude Code this week and write its steps as a plain list. Run the edge test: draw an arrow only where one step actually reads another's output. If arrows fall away, pick the smallest honest slice (one directory, one narrow question) and ask for it in plain words: use a workflow to <job>. Watch it under /workflows. If the run is good, press s to save the script to .claude/workflows/, and it becomes a slash command you can rerun whenever you want. And if you're still building the roster underneath all this, the multi-agent practical guide is the long version.

TL;DR

  • Slow "multi-agent" setups are usually a queue: agents waiting on each other with no data flowing between them.
  • The edge test: an "and then" is a real dependency only if the next step reads the previous step's output. Otherwise, run them at the same time.
  • The default shape is a diamond: fan out independent workers, merge results with plain code (zero tokens), let one agent judge.
  • Findings must survive a skeptic before they count; loops must dedupe against everything seen and stop after dry rounds.
  • Fan-outs cost real tokens. Opt in when one context can't hold the job, and put cheap models on the boring nodes.

FAQ

How do I make Claude Code run subagents in parallel?
Ask for it in plain words ("use a workflow to…") or put the keyword ultracode in your prompt. Claude writes a JavaScript orchestration script and runs it in the background while your session stays free. Requires Claude Code v2.1.154 or later on a paid plan; on Pro you enable Dynamic workflows in /config.

Do parallel fan-outs cost more tokens?
Yes. A workflow run can use meaningfully more tokens than working the same task in conversation, and Claude Code flags runs that schedule more than 25 agents or project past 1.5 million tokens. Gauge the spend on a small slice first: one directory, one narrow question.

What's the difference between a workflow and a subagent?
A subagent is a worker the main session spawns turn by turn, and its results land back in the context window. A workflow is a script that holds the whole plan: intermediate results stay in script variables, and only the final answer reaches your session.

When is a queue the right choice?
When steps genuinely feed each other, when the whole job fits one context window, or when the token budget matters more than the clock. A graph earns its cost on breadth: repo-wide audits, big migrations, research that needs cross-checking. Not on everyday tasks.
