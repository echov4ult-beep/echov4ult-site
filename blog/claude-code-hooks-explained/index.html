Claude Code hooks explained: automatic rules that always fire

2026-08-06 · echov4ult

Hooks are automatic scripts that fire at specific moments in Claude Code — before it runs a command, after it edits a file, when a session starts. Unlike instructions you put in CLAUDE.md (which Claude follows well but interprets on its own), hooks run every single time. They don't skip. They don't interpret.

The alarm-system version

Think of Claude Code as a contractor remodeling your house. CLAUDE.md is the sticky note on the fridge: "Don't touch the upstairs bathroom." Most of the time, the contractor reads it and respects it.

A hook is the motion sensor on the bathroom door. It doesn't need to be read. If the door opens, the alarm goes off. Every time. Automatically. That's what hooks do — they enforce rules whether Claude "remembers" them or not.

The four hooks worth knowing first

Claude Code has around thirty different moments where a hook can fire. If you're just learning what hooks are, four cover the ground.

PreToolUse fires right before Claude does something — runs a terminal command, writes a file, makes an edit. This is your chance to block it. If Claude is about to delete a folder or touch a file it shouldn't, a PreToolUse hook can stop the action before it happens.

PostToolUse fires right after Claude finishes doing something. The action already happened, so you can't undo it, but you can follow up. Run a code formatter on the file it just wrote. Check for style errors. Log what changed.

Stop fires when Claude finishes its entire response and is about to hand control back to you. This is the "final check" moment. Did it actually run the tests? Did it leave any placeholder code behind?

Notification fires when Claude pings you with an alert. If you want those alerts in Slack instead of the terminal, this is where you'd wire that up.

Where hooks live

Hooks go in a file called settings.json. Two locations:

~/.claude/settings.json (the ~ means your home folder) — your personal hooks, applied to every project you open.

.claude/settings.json inside a project folder — hooks that only apply to that project. These travel with the repo, so your whole team gets the same guardrails.

If both exist, they stack. Project hooks add to your personal hooks. They don't replace them.

What a hook actually looks like

Here's the simplest useful hook I could write. It runs a code formatter every time Claude writes a file:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write ."
          }
        ]
      }
    ]
  }
}

Three layers, inside out:

The hook itself: run Prettier (a code formatting tool) on the project. That's the "command" line.

The matcher: only fire this hook when Claude uses the Write tool. Not when it reads a file, not when it runs a terminal command. Just writes. That's the "matcher": "Write" line.

The event: PostToolUse — after the write is done, not before. That's the outer key.

Pick the moment, pick the trigger, pick what runs. That's the pattern for every hook you'll ever write.

Four things people actually build with hooks

Block a dangerous command. A PreToolUse hook on the Bash tool that checks if Claude is about to run rm -rf (the terminal command that deletes everything in a folder, no questions asked). If it matches, the hook blocks the command before it executes. Claude gets an error message. No files deleted. No close calls.

Auto-format on save. The Prettier example above. A PostToolUse hook that formats code every time Claude writes a file. You never ask Claude to clean up its formatting. It just happens.

Keep a log of everything. A PostToolUse hook that appends every tool call to a log file — which files Claude touched, which commands it ran, when. Simple, cheap, and surprisingly useful when you're reviewing what happened in a long session.

Lint after every edit. A PostToolUse hook on the Edit tool that runs your linter (a tool that checks code style and catches common mistakes). If Claude introduces a style violation, you know immediately instead of three steps later when something breaks.

Hooks vs. CLAUDE.md — different jobs, same team

This is the question I see most often, and it confused me too at first.

CLAUDE.md tells Claude how to think. Use this voice. Follow this pattern. Prefer this library. It's guidance. Claude reads it, interprets it, and follows it. Usually faithfully, but it's still interpretation.

Hooks don't talk to Claude at all. They're scripts that run alongside Claude, reacting to what it does. Claude doesn't decide whether to "follow" a hook. The hook fires because the event happened. Period.

In simple terms: use CLAUDE.md for preferences. Use hooks for hard rules.

They work best together. CLAUDE.md says "always write tests." A Stop hook checks whether tests actually ran before Claude finishes its response. The instruction shapes behavior. The hook verifies the outcome.

If you're sorting out the other moving parts in Claude Code — skills, subagents, commands — I wrote a breakdown of how those pieces fit together. Short version: skills are reusable instructions, subagents are independent specialists, commands are shortcuts, and hooks are enforcement. Different tools, different jobs.

When hooks earn their keep

  • You have a rule that must never be broken. Not "usually followed." Never.
  • You want something to happen automatically, without relying on Claude to remember.
  • You need a record of what Claude did. Logging hooks are cheap and surprisingly useful.
  • Your team shares a project and you want the same guardrails for everyone — project-level hooks travel with the repo.

When to skip them

  • You just want Claude to follow a convention. CLAUDE.md is simpler and adds no overhead.
  • The rule has gray areas. Hooks are yes-or-no. If the answer is "it depends," that belongs in instructions, not a hook.
  • Nothing has broken yet. Building guardrails for problems that haven't happened is how you end up maintaining scripts you forgot why you wrote.

Try it yourself

Pick one thing Claude does that you always double-check by hand. Maybe it's formatting. Maybe it's running tests. Write one PostToolUse hook that does the check automatically. Start there — one hook, one rule. You can see everything you've configured by typing /hooks inside Claude Code.

FAQ

Do I need to know how to code to use hooks?
A little. The simplest hooks are one-line commands — run a formatter, check a file. You can copy those from examples and they'll work. More complex hooks that inspect what Claude is about to do need basic scripting. But the concept isn't complicated, and starting with a copy-paste hook is perfectly fine.

Do hooks slow Claude down?
A fast hook (running a formatter, appending to a log) adds barely noticeable time. A slow hook (running a full test suite) adds whatever the tests take. Keep hooks focused and they stay fast.

What happens if my hook script crashes?
Claude keeps going. A broken hook is treated as a warning, not a wall. The error gets logged, but Claude's work continues. The one exception: if your hook deliberately exits with code 2, that's the signal for "stop, this action is blocked." Anything else is treated as a hiccup.

Are hooks the same as git hooks?
Same idea, different system. Git hooks fire on git events (commit, push). Claude Code hooks fire on Claude events (running a command, editing a file). You can use both at the same time. They don't interfere with each other.
