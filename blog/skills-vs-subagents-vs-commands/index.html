Claude Code: skills vs. subagents vs. commands — which one do you actually need?

2026-07-27 · echov4ult

Quick answer: a skill teaches Claude how to do a repeatable job (it's instructions, loaded when relevant), a subagent is a separate specialist with its own context window and permissions (it's a coworker), and a command is just a shortcut that kicks one of those off (it's a doorbell). Most people who ask this question want a skill.

I got this wrong for weeks, so here's the explanation I wish someone had given me.

The kitchen version

Think of Claude Code as a very capable cook in your kitchen.

  • A skill is a recipe card taped inside the cabinet. The cook grabs it when the dish comes up. Same cook, same kitchen — just a proven procedure so they don't improvise your grandmother's sauce from vibes.
  • A subagent is calling in a second cook who only does desserts. They work at their own station (separate context window), they only touch the tools you hand them (scoped permissions), and when they're done they bring you the plate — not their whole mess.
  • A command is the bell you ring to order a dish. /make-dessert doesn't cook anything; it just starts the process with one word instead of a paragraph.

When each one earns its place

Reach for a skill when you've explained the same process to Claude twice. That's the tell. My rule — typed it twice, encode it. Skills live as markdown files (SKILL.md), so they're versionable, editable, and honestly kind of addictive to write once you start.

Reach for a subagent when the job needs independence rather than instructions. The whole value of my QA agent is that it doesn't share my main session's assumptions — it reads the work cold and says "this fails" without knowing how attached I am to it. Verdict roles (reviewer, critic, tester) and big read-heavy research jobs are subagent territory. A quick fix in a file you've been discussing for an hour is not — the main session already has the context, and spinning up a specialist just adds cost and a briefing step.

Reach for a command when a skill or workflow deserves muscle memory. Commands are the smallest of the three — a named trigger. In my own setup nearly every command just launches a skill.

The mistake everyone makes (I made it too)

Building a 40-agent roster because it demos well. It burns tokens re-briefing specialists who add no verdict, and when nine agents comment on everything, nobody's "no" means anything. I run ten agents for a full game-studio setup and most days six do the work. Small party, deep roles, real authority — that's the pattern that held up. (Longer version: small party vs. mega-roster.)

FAQ

Do subagents cost more tokens than skills?
Generally yes — a subagent starts cold and must be briefed, and its system prompt + context load are overhead a skill doesn't have. Skills are instructions in the current session; subagents are separate sessions.

Can a skill call a subagent?
Yes — a skill's instructions can tell Claude Code to delegate work to a named subagent. That's how workflow-style skills coordinate specialists.

Where do skills and subagents live?
Project-level: .claude/skills/ and .claude/agents/ in your repo. User-level versions apply across all your projects.

How many agents should I run?
Fewer than you think. Six well-designed roles cover a full build loop; add more only when a recurring question has no owner. If two agents could both "own" a task, your roster is too big.
