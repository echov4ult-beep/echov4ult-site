How to build a Claude Code subagent (step by step)

2026-08-06 · echov4ult

Five minutes from blank file to working subagent. The whole process, including the parts most guides skip.

You create a text file, drop it in a specific folder, and write a few lines telling Claude what this specialist should do. No coding required. No install process. Just a file. Everything below is about making that file actually good.

Want the conceptual overview first? What Are Claude Code Subagents? covers the what and why. This guide is the how — we're building one from scratch, right now.

What you need

  • Claude Code, up and running
  • Any project to try it in
  • About five minutes

No SDK. No build step. No sign-up.

Step 1: Make the folder and create the file

Claude Code looks for subagents in a specific folder inside your project. If that folder doesn't exist yet, create it. Open your terminal and run:

mkdir -p .claude/agents

That creates a hidden folder called .claude inside your project, with an agents folder inside it. This is where all your subagents live.

Now create the file:

touch .claude/agents/code-reviewer.md

You've just made a blank text file. Open it in any text editor — VS Code, Notepad, whatever you like. We're going to fill it in.

Quick note on placement. You have two choices for where to put this file:

  • Inside your project (.claude/agents/) — The subagent only works in this project. If you check it into version control, your teammates get it too.
  • In your home folder (~/.claude/agents/) — The subagent works in every project on your machine. Good for personal helpers you want everywhere.

For your first one, project-level is fine. You can always move it later.

Step 2: Add the settings block

At the top of your file, you add a small settings section. In Claude Code's world, this is called "frontmatter" — a few lines between triple dashes that tell Claude who this subagent is and what it's allowed to do.

Here's what it looks like:

---
name: code-reviewer
description: Reviews code changes for bugs, security issues,
  and readability problems. Use after making code changes or
  before committing.
tools: Read, Grep, Glob
model: sonnet
---

Here's what each line does:

name — The subagent's ID. Keep it lowercase with hyphens between words. This is how Claude refers to it behind the scenes.

description — This is the most important line in the file. Claude reads it to decide whether a task should go to your subagent. Think of it like a job description: "Reviews code changes for bugs, security issues, and readability problems" tells Claude exactly when to hand off work. Something vague like "helps with code" doesn't give Claude enough to go on.

tools — What this subagent is allowed to do. Think of it like permissions on a phone app — you're choosing what it can touch. Read lets it look at files. Grep lets it search through code. Glob lets it find files by name. That's all a reviewer needs — it reads your code and reports back. If you leave this line out, the subagent gets access to everything, which is usually more than you want. A reviewer that can also edit your files will start editing your files.

model — Which version of Claude powers this subagent. Your options: haiku (fast and cheap), sonnet (solid all-rounder), opus (heavy-duty reasoning), or inherit (uses whatever your main session uses). For code review, sonnet hits the sweet spot.

Only name and description are required. But tools and model are worth setting every time.

Step 3: Write the instructions

Everything below that settings block is the system prompt — the instructions that shape how your subagent behaves. This is where most people go wrong, usually in one of two directions.

Too little:

You are a code reviewer.

Claude already knows what code review is. This tells it nothing new. You'd get the same result just asking Claude directly, without a subagent at all.

Too much:

You are an expert senior staff principal code reviewer
with 20 years of experience across all programming
languages, providing comprehensive, thorough,
exhaustive analysis...

Adjective salad. Piling up titles doesn't change how Claude works. None of those words make the output better.

What actually works is telling the subagent what to focus on, what to skip, and how to report back. Give it a decision framework:

Review the code for three categories of issues, in this
priority order:

1. Bugs and security — anything that would break in
   production or create a vulnerability
2. Logic errors — things that run but produce wrong results
3. Readability — naming, structure, anything that would
   confuse the next person

For each issue, show the specific line, explain the problem,
and suggest a fix.

Skip style nitpicks like formatting and bracket placement
unless they hide a real bug. If the code looks solid, say
so — a clean review is a valid outcome, not a failure to
find problems.

Five short instructions. The subagent now knows what to prioritize (bugs over style), how to format its response (show the line, explain, suggest), and what not to waste time on (formatting nitpicks). These are the things that actually shape behavior.

Step 4: Try it out

If this is the very first subagent file you've created in a brand-new agents folder, restart Claude Code once. After that first time, Claude watches the folder and picks up new or changed files on its own — no restarts needed.

Now test it. You can ask Claude directly:

Use the code-reviewer to look at the changes in src/auth.js

Or describe a task that matches your subagent's description and see if Claude delegates on its own:

Can you review my recent changes for any issues?

When Claude delegates, you'll see a row in the transcript with the subagent's name — something like code-reviewer (Review code changes). That's how you know it worked.

Step 5: Tweak and improve

Your first version won't be perfect. That's normal. The file is just text — edit it, save it, and the next time Claude delegates to that subagent, it uses the updated version.

Things you might adjust after the first run:

  • Claude didn't delegate at all. Your description is probably too vague. Make it more specific about when this subagent should be called in.
  • The output was a wall of text. Add a line to the instructions: "Summarize findings as a numbered list. Keep it short."
  • It flagged things you don't care about. Add skip rules: "Ignore formatting issues" or "Don't review test files."
  • It started editing your code instead of just reviewing. Check whether Write or Edit are in the tools list and remove them. Or add "Report issues only — never modify files" to the instructions.

This edit-and-test loop is the whole workflow. No deploy step, no compilation, no waiting. Change the file, run a task, see what happens.

The complete file

Here's everything above put together — the finished subagent, ready to save as .claude/agents/code-reviewer.md:

Common mistakes

Making it too broad. "A general helper for all coding tasks" — that's just Claude Code itself. Subagents work best when they do one thing well. If you can't describe the role in one sentence, it's either two subagents or none.

Giving it too many permissions. Start with the minimum. A reviewer needs to read, not write. A researcher needs to search, not edit. You can always add tools later when you see it struggle without them. Going the other direction — figuring out which extra permission caused a mess — is less fun.

Copying your main conversation. Subagents start fresh every time. They don't know what you and Claude have been discussing. If a task needs all that context to work, just ask your main session directly. Subagents are for jobs you can hand off with a short description — like asking a colleague to look something over.

Writing a vague description. The description is how Claude decides what goes where. "Helps with code" is like a job posting that says "does computer things." Be specific: what does this subagent handle, when should Claude call on it, what kind of tasks match?

Stuffing the prompt with adjectives. "Expert senior staff principal" doesn't change output quality. Clear instructions do. Tell the subagent what to focus on, what to skip, and how to format its response. Skip the resume padding.

Once you're comfortable: more settings

The four fields above handle most real-world use cases. When you're ready to fine-tune, here are some additional options:

  • maxTurns — Limits how long the subagent can work. Useful if you don't want a research task running for fifty rounds.
  • isolation: worktree — Gives the subagent its own copy of your code to work in, so experimental changes don't touch your actual files.
  • disallowedTools — The flip side of tools. Instead of listing what's allowed, you list what's blocked. Handy when you want "everything except file editing."
  • mcpServers — Lets the subagent connect to external tools (like a Playwright browser or a Slack connection) that your main session doesn't load.
  • skills — Preloads specific Claude Code skills into the subagent's memory at startup.

The official docs cover every field in detail. But start simple: name, description, tools, model. Add the rest when you have a specific reason.

Frequently asked questions

Do I need to restart Claude Code after creating a subagent?

Only once — if it's the very first time you've created an agents folder. Claude Code watches that folder for changes, but it can only watch a folder that existed when your session started. A brand-new folder needs one restart. After that, new or edited subagent files get picked up automatically within seconds.

Should I put subagents in my project or my home folder?

Project folder (.claude/agents/) for anything tied to a specific codebase — check it into git so your team gets it too. Home folder (~/.claude/agents/) for personal tools you want available in every project. If the same name shows up in both places, the project version wins.

Can subagents create their own subagents?

Technically yes, up to a depth limit. Practically, keep things flat for now. Your main session hands off to a subagent, the subagent does the work and reports back. Nesting adds cost and latency at each layer, and you rarely need it.

Which model should I pick?

Match the model to the job. Haiku for quick, simple tasks like finding files or checking formatting. Sonnet for most review and analysis work — the best balance of smarts and speed. Opus for tasks that need deep reasoning, like untangling a tricky architecture problem. If you're not sure, sonnet is a safe default.

How many subagents should I have?

Fewer than you think. Each one is a file you need to keep accurate and updated. Three subagents you use every day beat fifteen you forget about. Start with one, get it working well, then add another when you have a clear repeated task for it. For more on right-sizing, Small Party vs. Mega-Roster covers the tradeoffs.

Try it yourself

Pick one task you repeat in most projects — reviewing code, scanning for TODOs, checking that tests exist for new functions. Build one subagent for it. Run it. Tweak the prompt. Run it again. The whole loop takes five minutes, and one real subagent you've iterated on teaches you more than reading about ten theoretical ones.
