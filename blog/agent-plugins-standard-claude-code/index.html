OpenAI just standardized Anthropic's plugin idea. Here's what that means for your Claude Code stack.

2026-08-06 · echov4ult

Agent Plugins, announced today by OpenAI with Amazon, Cursor, GitHub, Microsoft, and Vercel, is a shared format for packaging Agent Skills and MCP server configs so one plugin folder works across many AI clients. If you run a Claude Code stack: your skills were already portable, your MCP configs weren't, and this spec is aimed at that second problem — with Anthropic conspicuously absent from the table.

Here's the kitchen-table version. Imagine every appliance brand shipping its own shape of wall outlet. Your toaster works in the kitchen but not the garage. That's agent plugins in 2026: same skills, same MCP servers, different folder layout and manifest for every client. Agent Plugins is a group of vendors agreeing on one outlet shape.

I didn't have to look far for evidence that the problem is real. The superpowers plugin installed on my own machine ships a .claude-plugin/plugin.json for Claude Code, a .cursor-plugin/plugin.json for Cursor, a .codex-plugin/plugin.json for Codex, and an .opencode/ folder besides. Four manifests, nearly identical JSON, one plugin. Every plugin author is maintaining that same pile of duplicates right now.

What's actually in the spec

I read the spec at agent-plugins.org so you don't have to. Version 1.0.0 defines a plugin as a plain directory:

  • plugin.json — the manifest. Only two fields are required: $schema and name. Version, author, license, keywords are optional.
  • skills/ — Agent Skills, one folder per skill with a SKILL.md inside, following the existing Agent Skills specification. If you've written a skill for Claude Code, you've already written one of these.
  • mcp.json — MCP server declarations. Three connection types: stdio (a local process), streamable HTTP, and legacy SSE. Two placeholders, ${PLUGIN_ROOT} and ${PLUGIN_DATA}, so servers can find their own files.
  • Extension namespaces — reverse-domain folders like com.example.client/ where each client keeps its proprietary extras. Clients ignore namespaces they don't recognize.

Two things stand out to me after running plugins across a real multi-agent setup for a year.

First, the skills part is the least new thing here. Agent Skills is Anthropic's concept: it launched in Claude in October 2025 and Anthropic published it as an open standard in December 2025. The portable part of your stack was already portable. What Agent Plugins actually adds is standardized packaging around skills — the manifest, the MCP config, and a sanctioned junk drawer for client-specific features.

Second, the extension-namespace design is doing a lot of quiet work. Claude Code plugins carry things this spec doesn't standardize — hooks, slash commands, subagents. Under Agent Plugins those would live in a vendor namespace folder, which means "compatible with the standard" and "fully works in your client" are not the same sentence. Read launch-day compatibility claims with that in mind.

The elephant: where's Anthropic?

The launch clients are Codex, ChatGPT, Cursor, GitHub Copilot, Kiro, and VS Code. No Claude Code. The steering committee is Amazon, Cursor, Microsoft, OpenAI, and Vercel. No Anthropic.

That's a strange picture, because both building blocks of this spec — Agent Skills and MCP — started at Anthropic. The polite reading: Anthropic already open-sourced both pieces (MCP went to the Linux Foundation in December 2025), so a packaging spec on top doesn't need their permission. The less polite reading: the rest of the industry just formed a standards body around Anthropic's ideas without a seat for Anthropic, and "open standard" is partly a competitive move.

I don't know which reading is right, and I won't pretend to. What I do know is that standards fights get settled by adoption, not steering committees. If plugin authors start shipping one Agent Plugins folder instead of four manifests, clients that can't read it will feel the pressure — Claude Code included.

What I'd do about it today (and what I wouldn't)

Nothing about your current setup broke this morning. Your Claude Code skills, agents, and hooks work exactly like they did yesterday. My whole multi-agent Claude Code setup runs unchanged.

What I'd actually do:

  1. Keep writing skills the way you already do. SKILL.md in a folder is the shared atom of both worlds. Anything you write today rides along whichever way this goes.
  2. Keep client-specific logic out of your skills. If a skill shells out to Claude Code-only features, it won't travel. My skills vs subagents vs commands breakdown covers what belongs where.
  3. Don't rush to repackage. The spec defines no registry, no install command, no update mechanism — clients each decide how plugins get discovered and installed. Repackaging now means testing against six clients' interpretations of a day-old spec.

The boring truth about the toolkits I sell is the same truth: the durable part of an agent stack is the operating discipline and the skill files, not the packaging. Packaging formats churn. The Operator's Kit survives this announcement untouched for exactly that reason.

Try it yourself

Open your own plugins folder (~/.claude/plugins/ if you're on Claude Code) and count the manifests inside any third-party plugin you've installed. If you find two or more *-plugin/plugin.json files describing the same thing, you've found the exact problem this standard exists to solve — and you'll know why it might stick.

FAQ

Is Agent Plugins the same as Claude Code plugins?
No, but they rhyme. Both are folders with a plugin.json manifest, skills, and MCP config. Claude Code's format also carries hooks, slash commands, and subagents, which the shared spec doesn't standardize — those would sit in a client-specific extension namespace.

Do my existing Claude Code skills work with Agent Plugins?
The skill files themselves, essentially yes. The spec's skills/ directory follows the same Agent Skills specification Claude Code uses, one SKILL.md per skill folder. It's the wrapper around them that differs.

Does Claude Code support Agent Plugins?
Not at launch. The announced compatible clients are Codex, ChatGPT, Cursor, GitHub Copilot, Kiro, and VS Code. Whether Anthropic adopts the format is unknown as I write this.

What's the difference between Agent Plugins and MCP?
MCP is a protocol: how an agent talks to a tool server while running. Agent Plugins is packaging: how you ship skills plus the config that tells a client which MCP servers to start. A plugin's mcp.json declares MCP servers; it doesn't replace them.

Should I repackage my plugins for the new standard?
Not yet, unless you're actively distributing to users on multiple clients. The spec is a day old, defines no registry or install mechanism, and each client decides its own discovery story. Watch adoption for a few weeks first.
