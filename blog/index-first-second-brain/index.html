Why is my AI second brain slow and expensive? Because it's a pile, not a graph.

2026-07-27 · echov4ult

Quick answer: your AI second brain is slow and expensive because the model has to dig for answers instead of looking them up. The fix is structure, not a smarter model: a tiny router file the model reads first, a one-line-per-note index it can scan in a single pass, small one-idea notes, links only where one note depends on another, and retrieval done by plain code so the model runs once with the evidence already in hand.

My whole operation runs on plain text: an Obsidian vault, a memory folder my Claude Code sessions read at startup, briefing files for a small crew of agents. This week I audited all of it against an idea called graph engineering, from a long-form piece on X by @kingwilliam_. Credit to him for the shape of it. Everything below is that idea passed through my own setup, in my own words.

TL;DR

  • A pile of notes forces the model to search blind on every question. A graph gives it a map it can read in one pass.
  • The engine is the index: one line per note — name, link, one honest sentence. If you build only one piece, build this.
  • Keep the router file tiny (pointers, not content), keep notes small (one idea each), and add links only where one note needs another.
  • Let plain code do the finding so the model fires once, at the end, with the evidence attached.
  • I rebuilt my own vault's index this week — 115 notes, one line each. Receipts below.

Why the pile gets expensive

Most AI second brains are a folder of notes with a chat model pointed at it. That works until it doesn't. Every question becomes an expedition: the model searches for a keyword, opens a file, realizes it's the wrong one, opens two more, and finally answers with a context window full of things it never needed. You pay for every token it read along the way, and you wait while it reads.

In fairness to piles, tools like Claude Code don't read every file — they search. But keyword search only finds notes that share your keyword. Ask "why did we stop using the old deploy trick?" and the note holding the answer is titled something else entirely, so the model burns three or four tool calls narrowing down, and each dead end costs tokens and seconds.

The notes were never the problem. The missing structure over the notes is.

In simple terms

Picture two people who each own five thousand books. The hoarder keeps his in stacks on the floor. Ask him a question and he starts digging: twenty minutes, nine books pulled off the stacks, and you're paying him by the minute. The librarian owns the same five thousand books, but she also keeps a card catalogue — one card per book, one sentence saying what it's about. Ask her the same question and she reads a drawer of cards, walks to one shelf, and hands you one book.

Your AI assistant charges by the page it reads. A pile of notes turns it into the hoarder. A few small habits — a catalogue, thin books, a note on the front door saying where things live — turn it into the librarian. Same notes, same assistant, very different bill.

The five pieces, in build order

1. A router the model reads first

One tiny file at the top — for Claude Code that's usually CLAUDE.md — read at the start of every session. It holds rules and pointers: what lives where, what the conventions are, what to read next. Never the content itself. Mine is 39 lines. The original piece puts a hard number on it, under 500 tokens, and I like that as an audit rule, because a router that scrolls forever isn't a router anymore. It's a lobby with a couch.

This is the same reason a good subagent briefing stays short: everything the model reads before working is a tax on every single session. The entry file points; the explanations live one hop away.

2. The one-line index — this is the engine

One line per note: name, link, one honest sentence about what's inside. That's the whole trick, and it's the piece I'd rebuild first if I lost everything else.

Here's why it wins. A model can read a 115-line index in one gulp and score every note in your vault by meaning, instead of by whether your question happened to share a keyword with a filename. One read, one shortlist, straight to the right file. My vault's version went live this week: _index/CATALOGUE.md, 115 notes, each entry formatted name | folder | one sentence, with a standing rule that any note created, renamed, or moved gets its line updated in the same turn. That last rule is the one that matters, because an index that drifts is just a second pile.

And to say the quiet part out loud: Obsidian's glowing graph view, the constellation everyone screenshots, is wall art. Genuinely nice wall art. The machine never looks at it. The index is the part the machine uses.

3. Small notes, one idea each

When a note answers exactly one question, the model can read exactly one note. My Claude memory folder is the strict version of this: every memory is its own small file — one lesson, one project, one rule — and the top-level MEMORY.md gives each file a single line with a hook. A session that needs the lesson from my card-listing app opens that one file and nothing else.

Long sprawling notes fail in the other direction: the model finds the right file and still has to wade through it. Or worse, it quotes the wrong half.

4. Links only where one note needs another

A link earns its keep when it marks a dependency: to understand this note, you need that one. Linking everything vaguely related feels productive and quietly rebuilds the pile, because the model can't tell a load-bearing edge from a vibe. My vault's floor rule is one link minimum, so nothing gets orphaned. The ceiling rule I'm adopting from the article is stricter: if the model wouldn't need to follow a link to answer, it's decoration.

5. Retrieval as boring code

The last piece changes the bill the most: don't let the model rummage. Strip the question to keywords with code. Score the index lines with code. Open the single best note, pull the section that answers, follow at most one link if it points to a dependency — all of it deterministic, all of it free after you write it. Then the model runs once, at the end, with the evidence sitting in front of it.

Model calls are the expensive, wobbly step; a script costs nothing per run and returns the same result every time. Spend the model where judgment lives, and let code do the walking.

What I actually run (the receipts)

Scoring my own setup against the five pieces, honestly:

  • Router: yes. The vault's CLAUDE.md is 39 lines of rules and pointers.
  • A router layer for agents: yes. An _index/ folder — current state, map, agent roster, glossary — written for machines, terse on purpose.
  • One-line index: as of this week, yes. The new catalogue covers 115 notes across my Projects, Areas, and Resources folders, and my memory system has run the same pattern for months.
  • Small notes: yes. A bit over 200 markdown files in the vault, one idea per resource note, one fact per file in memory.
  • Retrieval as code: partial. I have deterministic knowledge-graph maps for my codebases, but the vault script that scores the catalogue and opens a single note is still on the list.

Four and a half out of five, and the missing half is the piece with the biggest payoff. That's this month's project. The same files-first discipline is also the backbone of how I run my agent crew — the long version of that story is in the multi-agent setup guide.

Try it yourself

Skip the plugins and the vector database for now. Tonight, make one new file at the top of your notes folder — INDEX.md — and give every note one line: name, link, one honest sentence. Then adopt the single rule that keeps it alive: a new note gets its line the same day it's born. That one file is most of the distance between a pile and a graph, and it costs you an evening. FAQ

Do I need a vector database for an AI second brain?
Not at the scale most people are actually at. I don't run one — a plain-text index plus the model's own search covers my two-hundred-note vault. Embeddings earn their keep when meaning-based lookup across thousands of documents starts failing, not before. The one-line index is free, and you can read it yourself.

What goes in the router file, and what stays out?
Rules, conventions, and pointers — never the content. "Finances live here, the state file is there, update the index when you change the system." If a fact matters, it lives in a note and the router says where. The piece that inspired this suggests staying under 500 tokens; my vault's router is 39 lines.

Isn't linking all my notes together the same as a knowledge graph?
No — dense linking rebuilds the pile with extra steps. A link helps the model only when it marks a dependency worth following. When every note points to twelve others, no link means anything and retrieval wanders.

How much does this actually save?
I owe you a receipt and don't have one yet. The author of the original piece reports a rebuild that came back roughly 40% cheaper — his build, his number, and I haven't verified it. My plan is a head-to-head: the same questions through a flat session and an indexed one, comparing tokens and wall clock. Whatever the numbers say, they get published.
