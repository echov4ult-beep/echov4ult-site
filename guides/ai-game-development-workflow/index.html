Pillar guide

The AI game development workflow

Updated 2026-07-26 · echov4ult

A repeatable loop from first concept to release check — designed for one human developer working with an AI team that pushes back.

The core problem: an assistant that always says yes

AI assistants are agreeable by default. Ask for a feature, get a feature — whether or not it breaks your game's pillars, your economy, or your schedule. A workflow fixes this by inserting named checkpoints where "no" is a legal answer. Here is the loop we run, stage by stage.

Stage 1 — Vision and pillars (once)

Before any feature work: a one-page vision (what the game is, who it's for, the core fantasy) and 3–5 pillars — the properties every feature must serve. Pillars are the cheapest scope-control tool that exists: "does this serve a pillar?" kills a bad feature in one sentence, weeks before it would have cost you a month.

Stage 2 — Feature proposals, not feature requests

Every non-trivial change starts as a written proposal: what it is, which pillar it serves, what it touches, what it costs. The design lead (human or agent) reviews it against the pillars; systems roles flag economy and balance impact. Most bad ideas die here, in a document, where dying is free.

Stage 3 — Scope check

A proposal that survives design review gets a scope pass: is this a day, a week, or a month? What's the smallest shippable version? What gets cut first if it overruns? Recording the answer turns "it's taking longer than I thought" from a crisis into a pre-made decision.

Stage 4 — Specification and handoff

Implementation starts from a written spec: acceptance criteria, edge cases, save/load implications, what "done" means. If you work with an AI engineer agent, the spec is the prompt — and the difference between a spec-driven session and a vibe-driven session shows up immediately in rework.

Stage 5 — QA gates with teeth

Two separate checks, run by different roles if possible:

  • QA review: does it work? Edge cases exercised, save/load verified, regressions checked.
  • Quality critique: is it good? An adversarial pass with a verdict scale, empowered to say Major Revisions Required.

The gate only works if failure is a real outcome. In Full Party's worked example — a fictional cozy game called Lanternfall Grove — the Quality Critic fails the crafting system on the first pass, and the loop (revision → re-review → approved) is shown in full, because that loop is the product working as intended, not an embarrassment to hide.

Stage 6 — Decision log, always

Every stage that reaches a verdict writes one line: ID, date, what was decided, who decided. This is what stops the most expensive failure in solo development — re-arguing settled questions every session because nobody remembers why the answer was no.

Stage 7 — Release check

A final checklist pass before anything ships: builds clean, saves migrate, store assets exist, known-issues list written, rollback plan named. Boring on purpose. Ship-day surprises are all the excitement you'll ever need.
