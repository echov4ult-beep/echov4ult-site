Multi-agent Claude Code: the practical guide

Updated 2026-07-26 · echov4ult

A team of specialist agents beats one general assistant — but only if you build the team like a team: defined roles, defined authority, and checks that actually run.

Start with the unit: what a subagent is

A Claude Code subagent is a markdown file — a name, a description of when it should be used, an optional tool allowlist, and a system prompt. Claude Code delegates work to it in a separate context window, and it reports back. That's the whole mechanism. (Longer explainer: What are Claude Code subagents?)

The mechanism is trivial. The value is in the design — and most multi-agent setups fail at design, not configuration.

Rule 1 — One agent, one question

The failure mode of agent design is the do-everything agent with a personality bolted on. An agent earns its place by answering exactly one question:

  • Game Director: does this belong in the game?
  • QA Director: does this actually work?
  • Code Reviewer: is this safe to merge?
  • Player Advocate: will a player enjoy or understand this?

Each agent needs three things beyond its question: a verdict scale (e.g. Approved / Approved with Revisions / Major Revisions Required / Rejected), boundaries (what it must not do — the Art Director doesn't write code), and required context (what it reads before it speaks).

Rule 2 — Small party, deep roles

There are repositories with 50+ ready-made agents, and they demo beautifully. In practice, big rosters burn tokens re-explaining context to agents that add no verdict, and every added agent dilutes authority: when nine agents comment on everything, no agent's rejection means anything. Six well-designed roles cover a full concept-to-ship loop for a game project. Ten is a full house. (The full argument: Small party vs. mega-roster.)

Rule 3 — Governance is the product

Agents disagreeing is a feature — unresolved disagreement is a bug. Before adding a fifth agent, write down:

  • Authority map — who decides what, and whose verdict wins per domain.
  • Decision log — decisions get an ID and a date, in a file. A decision that isn't recorded will be re-litigated, by you or your agents, within a week.
  • Escalation rules — what happens on deadlock (usually: it goes to you, with each side's one-paragraph case).
  • Definition of Done — what "finished" requires: tests run, docs updated, decision logged.

Plain markdown is enough. What matters is that the files exist and agents are told to read them.

Rule 4 — Nothing ships checked once

Every artifact gets a second, adversarial pass — same agent, new instruction: "find what's wrong with this." AI work fails silently more often than loudly; a stale test log looks exactly like a fresh one. The recheck is the cheapest insurance in the whole system. (War stories: The recheck rule.)

Rule 5 — Test the setup like software

If your agent kit installs anything, write acceptance scenarios: clean install, re-install, upgrade, uninstall, weird paths, pre-existing files. Then sabotage-test the checks themselves — break something on purpose and confirm the check fails. A check that can't fail isn't a check. (How we do it: Acceptance-testing an AI kit.)
